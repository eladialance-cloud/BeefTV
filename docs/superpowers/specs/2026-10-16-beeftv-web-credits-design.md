# BeefTV 网页版多用户积分平台设计

状态：待评审
日期：2026-10-16

## 1. 目标与产品边界

把 BeefTV 从单机本地创作工具改造成多用户网页版创作平台。本设计覆盖一个由五个阶段组成的整体计划，包含三件事：

1. 网页版可对外服务，用户之间数据互不可见；
2. 用户端按积分扣除，支持充值支付；
3. 把漫剧老李 AIGC 全流程 Skill 接入平台。

整体计划的成功标准：

- 用户可注册、登录，画布、项目、素材、任务、模型配置互不可见。
- 提交生成任务时按积分预冻结，任务结束按实际用量结算，失败或取消全额退还。
- 用户可下单充值，支付回调入账具备幂等，后台可对账、可退款。
- 管理员可在后台配置模型渠道、积分价格规则、赠送额度、用户与订单。
- 管理员可在后台**添加**支付渠道配置与对象存储配置，无需改代码或重启发版。
- 漫剧老李技能包可由平台 Agent 调用并产出稿件。

明确的非目标：内容社区、创作精选、模板市场、大赛运营。这些属于内容运营系统，与创作平台不是同一件事，留到后期单独立项。

## 2. 现状与可复用基础

改造前先确认哪些零件已经存在。结论是大部分是接线工作，不是从零造。

| 能力 | 现状 | 结论 |
| --- | --- | --- |
| 服务端形态 | `backend/cmd/server` 已是 Gin hosted profile，支持 `DATABASE_URL` | 可直接上 PostgreSQL |
| 身份认证 | `backend/internal/workspace/service.go` 单工作区 owner，无登录路由 | 必须新增 |
| 数据归属 | Resource、Task、Skill、Project 等模型普遍带 `UserID` / `OwnerID` | schema 层复用 |

| 凭据加密 | `backend/internal/localcrypto`、`managed_credential.go`、`encryptSystemChannelSecrets` | 支付与存储密钥加密复用 |
| 计费底账 | `model.ApiCallLog` 按用户、渠道、任务记录 token、媒体数、视频秒数、`EstimatedCostMicros` | 直接作为成本底账 |
| 预占与结算模式 | `backend/internal/asset/ports.go` 的 `Quota` 端口已是 Reserve / Release / Commit | 积分账本同构复用 |
| 系统配置 | `model.SystemSetting` | 后台配置落库 |

| 任务执行 | 进程内 local task worker | 必须换外置队列 |
| 前端 | Vite SPA，`web/src/router.tsx` 无登录路由 | 新增登录、充值、管理后台页面 |
| PostgreSQL 驱动 | `backend/go.mod` 仅有 `gorm.io/driver/sqlite` | 必须新增驱动与连接池分支 |

### 2.1 上游托管层的遗留线索（重要）

`backend/internal/database/local_schema.go` 里的 `hostedTables()` 列出了上游托管版**曾经存在、并在开源版被移除**的表。这是上游自研的托管 SaaS 数据模型，正好覆盖本设计要做的三件事：

```text
身份认证      auth_sessions, user_identities, oauth_states,
              email_verification_codes, users
对象存储      user_oss_settings, storage_locations
钱包与计费    model_pricings, credit_accounts, credit_ledger_entries,
              billing_orders, billing_reviews, topup_products,
              channel_model_price_tiers, logical_model_price_skus
支付          payment_provider_configs, payment_orders, payment_notifications,
              payment_reconciliation_runs, payment_reconciliation_items
兑换与活动    redeem_batches, redeem_codes
内容分发      announcements, announcement_image_drafts, user_announcement_reads,
              banner_announcements, canvas_shares
```

两条结论：

1. **本设计的表结构应与上游命名对齐**，而不是另起一套。这样 `hostedTables()` 清单、上游既有约定与后续可能拿到的托管代码都能对齐，迁移与回滚成本最低。本文档中的表名已按此调整。
2. 这些表对应的 **Go 模型、service 与路由在本仓库中已不存在**（`CreditAccount`、`PaymentOrder`、`PaymentProviderConfig` 等在全仓 0 命中）。开源版只保留了「表名清单」用于**删除**这些表。

由此引出一条硬约束，见第 8 节第 6 条。

## 3. 系统分层与角色

```text
用户端（创作台）        管理后台                平台服务
- 注册登录              - 模型与渠道            - 任务队列
- 画布与项目            - 积分与价格规则        - 对象存储适配
- 技能与 Agent          - 用户与权限            - 支付网关适配
- 积分与充值            - 订单与对账            - 成本与用量统计
- 账单与流水            - 支付渠道配置          - 凭据加密
                        - 对象存储配置
                        - 系统设置与审计
```

角色沿用 `model.UserRoleAdmin`，默认注册用户为普通用户。管理后台不单独建用户体系，权限由 `RequireAdmin` 统一校验，且必须在服务层校验，不依赖前端隐藏入口。

### 3.1 前端形态：本地工作台与托管工作台分开

仓库里 `web/` 是本地桌面版前端，且有一条硬边界：`web/test/local-only-source-boundary.test.ts` 要求
`src/pages/auth/login.tsx`、`src/services/api/wallet.ts`、`src/pages/admin/index.tsx`、`src/styles/admin-ui.css`
等托管入口**物理不存在**，这样桌面安装包不会携带 SaaS 控制面。

因此托管前台不放 `web/src`，而是独立成 `web-hosted/`（零依赖静态站点，与 `web/` 共用同一后端 JSON API）。
两个前端各自部署、各自发布，边界不会随着功能增加而变浑。

## 4. 用户端积分体系

### 4.1 计价原则

积分是平台内部点数，不直接等同于人民币。人民币只用于购买积分包与创作套餐。这样做的原因有两条：上游模型按秒调价时，只需调整价格规则系数，用户侧价格可以保持稳定；同时避免把平台做成虚拟货币发行方带来的合规问题。

### 4.2 三段式扣费合同

沿用 `Quota` 端口的预占模型：

1. 预冻结：任务提交时按价格规则计算预估积分，校验余额充足后冻结，余额不足直接拒绝，不允许透支；
2. 执行：任务运行期间不改动用户余额；
3. 结算：成功后按实际用量扣减并释放多余冻结；失败或取消时全额释放。

幂等键为 `task_id + attempt + stage`：`attempt` 首次提交为 1，用户主动重试递增，因此重试不会被上一轮的键重放吞掉，同一 attempt 内的重复回调又必须收敛到同一笔账。

实现入口：`backend/cmd/server/task_cost.go` 的适配器实现任务域窄接口 `task.Cost`，在 `internal/task` 的提交、重试、取消和 `internal/app` 的终态协调器里调用。`internal/task` / `internal/app` 不依赖 `credits`，保持桌面二进制边界。

### 4.3 价格规则

价格规则落库，管理员可改，不需要发版。命名对齐上游：

| 表 | 用途 |
| --- | --- |
| `model_pricings` | 模型级价格 |
| `channel_model_price_tiers` | 渠道 × 模型的价格档 |
| `logical_model_price_skus` | 逻辑模型 SKU 选择器与价格 |
| `task_cost_charges` | 每个任务尝试的报价快照与冻结/结算状态 |

定价维度：渠道 / 模型、能力（文本 / 图片 / 视频 / 音频）、分辨率与时长档、单价、生效区间。改价后新老任务按生效区间分区计费。

### 4.4 账本与不变量

两张表，命名对齐上游：

- `credit_accounts`：用户余额与冻结额，带 `version` 做乐观锁，避免并发提交导致的超扣；
- `credit_ledger_entries`：不可变流水，含幂等键、任务 ID、类型（充值、消费、退还、赠送、人工调整）、变更前后余额、操作人、原因。

必须成立的不变量：

- 余额恒不为负；
- `balance + frozen` 等于流水累计结果；
- 每一笔消费都能追溯到具体任务，每一笔人工调整都有操作人与原因。

## 5. 支付与充值

### 5.1 范围

支付阶段只做一条完整链路：充值下单、支付、回调入账、对账、退款。

### 5.2 渠道与资质前提

首发支持支付宝电脑网站支付与微信支付 Native 扫码。两者的前提是具备营业执照（企业或个体户）并开通对应商户号，资质申请有周期，需要与开发并行准备。第三方聚合支付虽然接入快，但资金结算与合规风险较高，不作为主路径。

渠道不写死在代码里，见 5.5；新增渠道通过后台配置接入，代码侧只维护渠道适配器。

### 5.3 支付合同与表

| 表 | 用途 |
| --- | --- |
| `topup_products` | 充值商品（积分包 / 创作套餐） |
| `payment_provider_configs` | 支付渠道配置（后台添加） |
| `payment_orders` | 充值订单，`out_trade_no` 唯一 |
| `payment_notifications` | 渠道回调原始记录，用于幂等与排障 |
| `payment_reconciliation_runs` | 每日对账批次 |
| `payment_reconciliation_items` | 对账差异明细 |
| `billing_orders` | 账务订单，与积分入账关联 |
| `billing_reviews` | 异常订单人工复核 |

- 回调幂等：以 `out_trade_no` 收敛，重复回调不重复入账，原始回调写入 `payment_notifications`；
- 对账：每日拉取渠道账单与本地订单核对，差异写入 `payment_reconciliation_items`；
- 退款：后台发起、原路退回，同时在积分流水写负向记录；
- 风控：单笔与单日充值上限、异常订单人工审核开关，均由后台配置。

### 5.4 商品形态

售卖积分包与创作套餐，不售卖可直接提现的余额。首充赠送、赠送比例由后台配置。

### 5.5 支付渠道配置入口（管理后台）

后台提供「支付渠道 → 添加」入口，管理员表单化新增渠道，不需要改代码或重新部署：

- 可选渠道类型：支付宝、微信支付，后续可扩展；
- 填写项：渠道标识、商户号（AppID / MchID）、密钥与证书、回调地址、支持的支付方式、启用开关、排序；
- 密钥与证书必须加密存储，复用 `internal/localcrypto` 与现有渠道密钥加密方式；后台只回显掩码，不返回明文；
- 每个渠道提供「连通性测试 / 发起测试下单」，未通过测试的渠道不允许对用户开放；
- 支持多套配置并存与启停，便于灰度或切换商户号；
- 回调地址必须在后台可见可复制，便于在支付平台侧配置白名单。

## 6. 对象存储配置入口（管理后台）

对象存储配置落两张表，命名对齐上游：

- `storage_locations`：平台级存储配置，管理员添加；
- `user_oss_settings`：用户或租户级存储绑定（保留给后期 BYO 存储场景，本期可只读占位）。

后台提供「对象存储 → 添加」入口：

- 可选类型：S3 兼容、阿里云 OSS、腾讯云 COS、七牛，首发至少支持 S3 兼容与 OSS；
- 填写项：配置名称、接入点 / Endpoint、Region、Bucket、AccessKey、SecretKey、CDN 或自定义域名、路径前缀、是否默认；
- 密钥加密存储，后台只回显掩码；
- 提供「连通性测试」（连接、写入、读取、删除一条测试对象），未通过的配置不允许设为默认；
- 支持多套配置并存，可指定「默认存储」用于新资源写入，历史资源仍按其记录的位置读取；
- 配置变更必须留审计记录（谁、何时、改了哪一项，不含明文密钥）。

关键约束：

- 存储配置属于运行时数据，落库，不放环境变量；数据库连接本身仍是环境变量或配置文件；
- 已有资源的位置信息必须随资源记录持久化，切换默认存储不能让历史素材失效；
- 首次部署若库内没有任何存储配置，需要引导管理员在初始化向导中先添加一条，避免上传路径处于未定义状态。

## 7. 管理后台范围

原则是：凡是会随运营变化的，都不写进代码。分八类：

1. 模型与渠道：系统渠道增删改查、复制、启停、密钥、模型目录与别名映射；
2. 积分与计费：价格规则、计费系数、注册赠送额度、活动与首充赠送、兑换码、人工加减积分（带审计）；
3. 用户与权限：用户列表、封禁、角色、登录方式开关（密码 / 邀请码 / 第三方）；
4. 订单与对账：订单查询、补单、退款、对账差异处理；
5. **支付渠道配置：添加入口、编辑、启停、密钥掩码、连通性测试**（新增）；
6. **对象存储配置：添加入口、编辑、默认存储指定、连通性测试、审计**（新增）；
7. 内容与模板（后期）：内置技能上下架与编辑、画布与短剧流水线模板、漫剧老李导演风格候选卡、首页公告；
8. 运营与安全：系统设置、调用日志与成本报表、上传配额策略、限流与审核词表。

其中第 1、8 类基本是给已有服务层补路由与页面；第 2、3、4、5、6 类是新增。

## 8. 多用户基础设施改造

六件必须做的事：

1. 认证：新增 `internal/auth`，会话中间件注入用户后，全仓 `currentUser(c, svc)` 的调用点无需修改，这是最低侵入的切入点；
2. 租户隔离：`workspace` 包从单 owner 改为按会话用户取工作区，所有 repository 查询强制带用户归属；
3. 对象存储：把本地资源目录抽象为存储端口，具体实现由后台配置驱动（见第 6 节），否则多机部署读不到文件；
4. 任务队列：进程内 worker 换为外置队列，视频生成耗时长，多用户并发必然阻塞；
5. 数据库：SQLite 换 PostgreSQL，并补齐迁移与备份；
6. **迁移按 Profile 分流（硬约束）**：`bootstrap/runtime.go` 目前**不区分 Profile**，无论 server 还是 desktop 都执行 `database.MigrateLocalSchema`；而该函数会调用 `dropHostedTables()` **删除**第 2.1 节列出的全部托管表。这意味着只要 server profile 继续走本地迁移路径，新加的 `credit_accounts`、`payment_orders`、`storage_locations` 等表会在启动时被删掉。改造必须先让 schema 迁移按 Profile 分流：desktop 继续走本地 schema，server 走独立的托管 schema 迁移路径，且 `dropHostedTables` 只允许在 desktop/本地路径执行。

## 9. 漫剧老李 Skill 融入

- 技能包通过 `agent-host/skill-resource.mjs` 挂载，多目录按需读取，不塞进 `skills.json`；
- 六道前置锁由对话追问改造为网页向导；
- `validate_prompt.py` 等 Python 机检脚本以 sidecar 服务形式接入，后端 Go 通过内部接口调用；
- 计费互动点：经 Agent 调用技能产生的模型消耗同样计入积分扣费。

## 10. 分期与交付

| 阶段 | 内容 | 预估 |
| --- | --- | --- |
| P0 | 托管运行基座：PostgreSQL 驱动与连接池、Profile 分流的 schema 迁移、对象存储端口与后台添加入口、部署 | 3~5 周 |
| P1 | 账号体系 + 积分账本 + 管理员发积分 + 渠道后台 | 4~6 周 |
| P2 | 支付充值：支付渠道配置入口、下单、回调、入账、对账、退款 | 3~4 周 |
| P3 | 漫剧老李技能包接入 + 六道锁向导 | 3~4 周 |
| P4 | 公开注册、兑换码与活动、模板与内容运营 | 待评估 |

支付单独成阶段，因为它涉及资质申请、对账与退款流程，混进 P1 会拖慢账号与积分体系的交付。

对象存储配置入口放在 P0，因为它决定资源能否多机读取，属于前置依赖，晚做会导致 P0 之后的上传数据需要迁移。

本文件是程序级设计，不是单一实施计划。P0 到 P4 每个阶段都需要各自拆分出该阶段的设计与实施计划；P0 与 P1 之间存在依赖关系（P1 的租户隔离依赖 P0 的数据库与存储改造），P2、P3 可与 P1 后半段并行。

## 11. 风险

- **托管表被本地迁移删除**：见第 8 节第 6 条，这是当前代码里最直接的数据丢失风险，必须在引入任何托管表之前先完成 Profile 分流；
- 支付资质申请周期不可控，需与 P2 开发并行准备，且要准备未获批时的降级路径（管理员发积分）；
- 切换对象存储后，历史资源必须仍能按原位置读取，跨存储迁移需要单独的迁移任务与校验；
- 存储与支付密钥进入数据库后，密钥轮换与备份加密策略必须同步确定，否则数据库备份会成为凭据泄露面；
- 长时任务队列在多用户并发下的成本与排队体验，需要在 P0 阶段就确认并发与限额策略；
- 上游模型价格波动直接影响毛利，成本底账与用户定价必须解耦；
- Python 机检脚本与 Go 后端跨语言调用增加部署复杂度，需要明确 sidecar 的部署与健康检查方式。

## 12. 成功标准

- 两名用户互相看不到对方的项目、画布、素材与任务；
- 一次生成任务的积分冻结、结算、退还三条路径均有流水且可对账；
- 一笔充值从下单到入账可完整复现，重复回调不产生重复积分；
- 管理员可在后台完成渠道配置、价格调整、手动发积分、订单退款；
- 管理员可在后台新增一条对象存储配置并通过连通性测试后设为默认，新上传资源写入该存储；
- 管理员可在后台新增一条支付渠道配置并通过测试下单，用户端可见该渠道；
- 漫剧老李技能包可完成一次端到端的短剧稿件产出。
